BAGIAN I — VISI UTAMA
1. Tujuan akhir
Membangun satu aplikasi Android yang berfungsi sebagai pusat analisis website dan pengelolaan proyek web.
Pengguna memasukkan URL, aplikasi melakukan pemeriksaan sesuai akses yang tersedia, menyusun peta struktur website, mencatat endpoint dan dependensi, menyimpan resource yang diizinkan, serta menghasilkan proyek yang dapat diedit dan diekspor.
Untuk website milik sendiri atau yang mendapatkan izin, sistem juga menyediakan alur untuk mengganti konfigurasi backend lama dengan API baru, menguji integrasi, dan melakukan hosting ulang.
Sasaran akhirnya adalah menghasilkan proyek website yang dapat dikelola secara mandiri, bukan sekadar tangkapan layar atau daftar URL.
2. Definisi Full Access
Istilah Full Access dalam proyek ini berarti fitur analisis selengkap mungkin terhadap aset, konfigurasi, source code, endpoint, dan server yang memang dapat diakses secara sah oleh pengguna.
Ada tiga tingkat akses:
Level A — Public Inspection
Tanpa kredensial khusus.
Dapat memeriksa resource publik, halaman yang dapat dimuat, URL yang terlihat, metadata respons yang tersedia, dan informasi DNS publik tertentu.
Tidak menjamin source code asli, endpoint internal, atau seluruh konfigurasi server dapat diperoleh.
Level B — Authorized Project Access
Dengan izin pemilik dan akses yang sesuai.
Dapat memproses source code, konfigurasi deployment, spesifikasi API, aset privat yang diizinkan, log server yang disediakan, dan konfigurasi database yang boleh digunakan.
Level ini merupakan pilihan terbaik jika tujuannya membuat salinan proyek yang lengkap dan dapat dipelihara.
Level C — Owner-Controlled Rebuild
Untuk sistem yang dimiliki pengguna.
Dapat mencakup pemindahan domain, migrasi API, penggantian database, perubahan frontend, pengujian autentikasi, serta deployment ke infrastruktur baru.
Catatan: tidak ada tool yang bisa menjamin seluruh backend dan logika game pihak ketiga dapat diperoleh hanya dengan memasukkan URL. Komponen yang tidak tersedia harus diperoleh dari pemilik atau dibangun ulang secara terpisah.

BAGIAN V — API MIGRATION
15. Custom API: lama ke baru
Jawaban teknis: bisa, untuk sistem milik sendiri atau yang memiliki izin dan dokumentasi yang sesuai.
Rencana migrasi:
Tahap A — Inventarisasi
Mencatat endpoint lama yang diketahui, metode, skema, jenis autentikasi, serta komponen frontend yang memanggilnya.
Tahap B — Pemetaan kontrak
Membuat tabel pemetaan:
API lama
API baru
Status
/api/user
/api/v1/users/me
Direncanakan
/api/config
/api/v1/config
Direncanakan
/api/content
/api/v1/content
Direncanakan
Contoh path di atas bersifat ilustratif dan bukan endpoint yang ditemukan pada URL referensi.
Tahap C — Adapter layer
Membuat lapisan adapter untuk menerjemahkan request dan response frontend ke format API baru.
Tujuannya mengurangi kebutuhan mengubah setiap halaman secara terpisah.
Tahap D — Database baru
Menyusun skema database yang sesuai dengan kebutuhan aplikasi baru.
Data hanya dipindahkan apabila pemilik memiliki hak dan akses untuk melakukannya. Skema dan data backend lama tidak dapat disimpulkan secara lengkap dari URL frontend saja.
Tahap E — Authentication
Menyusun autentikasi baru, pengelolaan sesi, otorisasi, dan pembatasan akses.
Token API lama tidak boleh disalin atau digunakan ulang tanpa otorisasi yang sah.
Tahap F — Pengujian kompatibilitas
Menguji:
Request dan response.
Validasi data.
Error handling.
Login dan logout.
Session expiration.
Akses database.
Hak akses pengguna.
CORS.
Rate limiting.
Perilaku frontend ketika API gagal.
Tahap G — Cutover
Setelah pengujian berhasil, konfigurasi frontend diarahkan ke API baru.
Jika pemilik mengendalikan domain lama, proxy atau redirect dapat disiapkan sesuai kebutuhan. Jika domain lama bukan milik pengguna, aplikasi tidak dapat mengubah rute di server aslinya.
16. Mode integrasi API
Aplikasi menyediakan tiga mode:
Mode 1 — Direct New API
Frontend langsung menggunakan API baru.
Mode 2 — Adapter
Frontend menggunakan kontrak kompatibilitas yang diterjemahkan ke API baru.
Mode 3 — Mock API
API simulasi untuk menguji UI ketika backend belum tersedia.
Mock API tidak boleh disajikan sebagai layanan produksi yang benar-benar menyimpan atau memproses data asli.
